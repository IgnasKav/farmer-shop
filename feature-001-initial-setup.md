# Feature 001: Medusa foundation and 10,000-product storefront

Status: Ready for implementation planning  
Created: 21 October 2026  
Related plans: [Platform plan](hosted-commerce-platform.html) | [Lithuanian farmer pilot](lithuanian-farmers-pilot.html)

> Scope update: use the scraped Pilnas Puodas catalog instead of generating 10,000 synthetic products. The original sizing requirements below are superseded for this pilot. See [catalog seed instructions](farmer-commerce/apps/backend/scripts/PILNAS-PUODAS.md).

## Outcome

Set up a working local Medusa application, populate it with exactly 10,000 synthetic farm products, and connect a Vue + Nuxt storefront that makes the entire catalog browsable. A developer must be able to reproduce the environment from a clean checkout using documented commands.

This is the first implementation milestone for the Lithuanian farmer platform. The large catalog is a technical validation dataset, not an assumption that an individual farmer will sell 10,000 products. Use one demonstration farm and one database, consistent with the planned separate deployment per merchant.

“Display everything” means every published product is reachable through pagination and its own detail page. It does not mean loading 10,000 products into a single browser response.

## Scope

- Medusa backend and Admin, PostgreSQL, and any additional services required by the selected configuration.
- Custom Vue + Nuxt storefront connected to this backend through the Medusa Store API.
- Lithuania region, EUR pricing, one storefront sales channel, and a linked publishable API key.
- Deterministic, repeatable generation of 10,000 products with prices, images, categories, variants, and stock.
- Catalog listing, category filtering, basic text search, product detail pages, and responsive Lithuanian interface labels.
- Setup documentation and checks covering catalog completeness, seed recovery, and browsing performance.

Payments, checkout completion, delivery scheduling, DPD integration, customer accounts, merchant billing, and production deployment are separate features. Hide or clearly disable unfinished purchase actions in the demonstration storefront.

## 1. Bootstrap the project

Use the current stable Medusa v2 release and a separate Nuxt application with Vue and TypeScript. Record the exact Medusa, Nuxt, Vue, Node.js, PostgreSQL, and package-manager versions selected during implementation. Commit the lockfile and pin the runtime; subsequent installs must use the lockfile rather than resolve new versions.

Create the backend first, declining the optional storefront installation when prompted:

```sh
npx create-medusa-app@latest farmer-commerce
```

Run this once to create the application in a new `farmer-commerce` subdirectory beside these planning files. Inspect the generated backend structure and package scripts before writing setup commands. From `farmer-commerce`, scaffold the separate storefront:

```sh
npm create nuxt@latest apps/storefront
```

Use the generated Nuxt application as the custom storefront foundation. Inspect and reconcile workspace configuration and package-manager settings so the backend and storefront use a consistent install strategy. Preserve the backend layout generated by Medusa; do not assume older starter paths. Document exact development commands and distinct local ports for both applications.

Implementation tasks:

1. Verify the prerequisites for the selected Medusa release and document them, including Windows/PowerShell instructions.
2. Provide Docker Compose for local PostgreSQL with a persistent volume and health check. Add Redis only if required by the chosen application modules; document the decision.
3. Configure the backend database connection, local storefront/Admin origins, and authentication secrets through environment variables.
4. Commit `.env.example` files with placeholders; ignore real environment files. Keep Admin credentials and backend secrets out of browser bundles and source control.
5. Apply database migrations and document how to create the local Admin user.
6. Confirm backend health, Admin login, database persistence after restart, and storefront connectivity.

Keep the initial implementation on Medusa's supported modules and workflows. No custom marketplace or tenant layer is needed for this feature.

## 2. Configure one demonstration farm

Create or reuse these resources idempotently:

| Resource | Required configuration |
| --- | --- |
| Store | One clearly named demonstration farm |
| Region | Lithuania, country code `lt`, currency `eur` |
| Sales channel | One storefront channel containing all seeded products |
| Publishable API key | Linked to that channel and configured in the storefront |
| Stock location | One demonstration farm stock location linked as required for storefront inventory |
| Categories | Ten farm-related categories, 1,000 products each |
| Tax configuration | Explicit local demo settings sufficient for consistent price calculation; document assumptions without presenting them as production tax advice |

Suggested categories: vegetables, fruit, berries, herbs, mushrooms, grains, honey, preserves, dairy, and eggs. All records are synthetic and visibly described as demonstration data.

A valid product must be published, assigned to the storefront sales channel, and have a price resolvable in the Lithuania region. A record visible only in Admin does not satisfy this feature.

## 3. Seed exactly 10,000 products

Implement a custom Medusa CLI seed script using supported workflows, including `createProductsWorkflow`, rather than inserting product records directly into database tables. Invoke it through a project package script wrapping `medusa exec`.

### Dataset contract

Each product must have:

- A deterministic external seed key from `farm-demo-00001` to `farm-demo-10000`, stored in metadata, plus a unique stable handle.
- A readable Lithuanian title with a distinguishing sequence identifier, description, and category.
- Exactly one fixed-pack variant initially, with an appropriate option such as pack size and a globally unique SKU.
- A positive EUR price using the selected Medusa version's documented amount conventions. Verify one known fixture, such as EUR 2.50, renders as EUR 2.50 to catch unit conversion mistakes.
- A thumbnail and product image from a small set of local demo assets. Reuse assets across records; do not download 10,000 remote images.
- Inventory tracking enabled, backorders disabled, and inventory levels at the configured location. Set 100 deterministic variants to zero stock and the remaining 9,900 to positive stock to exercise availability states.
- Metadata identifying the dataset and its version so records can be safely found on subsequent runs.

There must be exactly 10,000 seed-owned products and 10,000 variants after a successful run. On a fresh demonstration environment, the storefront catalog must also total exactly 10,000: omit starter sample products or remove only explicitly identified starter fixtures. Never delete unrelated merchant data to meet a count.

### Repeatability and failure handling

- Generate the same data on every run, using a fixed random seed if randomness is necessary.
- Process bounded batches, initially 100 products, with limited concurrency. Avoid one enormous transaction or 10,000 simultaneous requests.
- Detect existing seed records by stable keys; skip or reconcile them rather than create duplicates.
- Reconcile missing prices, channel associations, and inventory after an interrupted run. Product existence alone is not proof that seeding finished.
- Prevent overlapping seed runs. Log progress, elapsed time, created/updated/skipped counts, and failed keys; exit unsuccessfully if any records remain incomplete.
- Support a small development count such as 100 and the full target of 10,000. Rerunning the full seed must converge to the full dataset.
- Require an explicit demo-environment guard. Do not run the bulk seed automatically when the backend starts or during production deployment.
- Any optional reset must target only tagged demo records and require explicit invocation; ordinary seeding must not reset the database.

## 4. Display the full catalog

Use the official Medusa JavaScript SDK (`@medusajs/js-sdk`) with the publishable API key and Lithuania region context. The SDK works independently of the storefront framework. Never use Admin API credentials in storefront code.

Implement the UI with Vue single-file components and Nuxt file-based routes. Use Nuxt SSR-aware data fetching (`useAsyncData` or `useFetch`) so initial catalog and product content is server rendered and hydration does not duplicate requests. Include page, category, search, and region in fetch/cache keys and refetch when route state changes. Use Nuxt runtime configuration for the backend URL and publishable key; only intentionally public values belong in public runtime config. Keep request-specific state isolated during SSR.

Use server-rendered Nuxt/Nitro deployment output for the performance checks, with product routes resolved on demand. Verify direct navigation, client navigation, and hydration without browser-only API errors. Adapt Medusa documentation examples to Vue composables rather than copying framework-specific components.

### Catalog page

- Display a responsive product grid with thumbnail, title, pack size, formatted EUR price, and availability.
- Fetch 24 products per page using server-side pagination. Show the matching total and page navigation, with stable ordering so products are not skipped or repeated on an unchanged dataset.
- Store page, category, and search query in the URL. Refresh, direct links, and browser back/forward must preserve the view.
- Apply search and category filters on the backend across the full catalog, not just the current page. Reset to page one when filters change.
- Use the supported product text query for basic title search; advanced fuzzy search and a separate search engine are outside this feature.
- Show loading, empty, invalid-page, and backend-error states with a useful recovery action.
- Request only fields needed for the view and load appropriately sized images lazily. Do not fetch the entire catalog to calculate pagination or filters.

With 24 products per page, the unfiltered catalog has 417 pages; the last page contains 16 products.

### Product page

- Resolve every product by its stable handle, including direct navigation and refresh.
- Display image, title, description, category, fixed-pack variant, EUR price, and stock availability.
- Keep out-of-stock products visible with a clear label.
- Return a proper not-found page for an unknown handle.
- Render product pages on demand; do not require generating all 10,000 pages during every development build.

Use Lithuanian interface labels and `lt-LT` number/currency formatting. Preserve Lithuanian characters correctly. Provide keyboard-accessible navigation, descriptive image alternatives, and a usable layout on mobile and desktop.

Document the cache policy. Product edits in Admin must reach the storefront within 60 seconds or through an explicitly documented invalidation mechanism.

## 5. Deliverables

- Generated application and storefront with pinned dependencies and committed lockfile.
- Local infrastructure configuration and environment examples.
- Seed generator, local image fixtures, and catalog verification script.
- Working catalog and product pages connected to real Medusa data.
- README covering infrastructure startup, installation, migrations, Admin creation, small/full seeding, development startup, checks, and shutdown without data loss.
- Recorded verification results and benchmark environment: runtime versions, machine resources, build mode, seed duration, and browsing timings.

Expose clear package scripts for seeding and verification. Document their exact names and working directories after inspecting the scaffold; example desired interfaces are `seed:catalog` and `verify:catalog`.

## Acceptance criteria

- [ ] A developer can follow the README from a clean checkout and open both Medusa Admin and the storefront.
- [ ] The full seed produces exactly 10,000 tagged published products and 10,000 variants, with all required relations complete.
- [ ] A second full seed creates no duplicates; an interrupted seed can be rerun to completion.
- [ ] The unfiltered Store API reports 10,000 products in the fresh demo environment. A bounded paginated verification finds 10,000 unique product IDs, all belonging to the expected dataset.
- [ ] Every product is reachable through catalog pagination. The first, middle, and last pages render correctly; page 417 has 16 products.
- [ ] Category counts match the seed contract. Search can locate a known product outside the first page, and URL state survives refresh/back navigation.
- [ ] Product detail pages work for representative records from the beginning, middle, and end of the dataset, including zero-stock products and a missing handle.
- [ ] Known fixture prices and Lithuanian characters display correctly; images resolve without external network dependencies.
- [ ] Changing a product title or price in Admin becomes visible according to the documented cache policy.
- [ ] Browser requests retrieve bounded pages, never the full 10,000-product catalog. No backend secrets appear in client code or responses.
- [ ] Production builds and project type/lint checks pass. Focused integration tests cover seeding invariants and Store API visibility; browser smoke checks cover listing, filters, and details.

### Performance validation

Use a production-mode local build against the full dataset. On a documented reference machine, target a warm catalog API p95 below 1 second over at least 50 requests spread across early, middle, and late pages at concurrency 5, with no failed requests. Target mobile Lighthouse LCP at or below 2.5 seconds for the catalog over three runs, recording the preset and results. These are initial engineering targets, not measured claims or production SLAs; investigate and document misses before considering the feature complete.

## Implementation sequence

1. Scaffold and pin versions; bring up the database, backend, and Admin.
2. Configure the region, channel, key, and stock location.
3. Seed 100 products and verify prices, images, channel visibility, and inventory.
4. Connect the storefront and complete listing, filtering, pagination, and detail pages.
5. Seed 10,000 products; verify completeness, reruns, interruption recovery, and performance.
6. Finish the README and record acceptance results.
